# 红线：人机协作的边界

> 核心观点：AI 时代工程师的价值不在"会写代码"，而在**给 AI 划边界**。
> 以下红线来自真实项目教训——每一条背后都有一次"AI 越权导致的返工"。

## 开发铁律（7 条，最高优先级）

| # | 红线 | 为什么 |
|---|---|---|
| 1 | **AI 只做代码层**：开发 / 审核 / 优化建议 | 职责边界清晰，人才是最终决策人 |
| 2 | **不打包、不部署、不启动服务、不测试接口** | 部署动作影响面大，必须由人执行、人看着 |
| 3 | **DDL 只出脚本文件，绝不执行 SQL** | 数据库是生产资产，执行权在用户手里 |
| 4 | **改代码前先给方案，确认后再实施** | 先确认逻辑 → 实施测试 → 通过后完善，避免大方向返工 |
| 5 | **严禁乱改配置文件**（application.yml 等） | 配置是环境契约，AI 想象中的"顺手修正"就是事故 |
| 6 | **涉及生产/现场改动，改前先 git 备份/确认版本** | 有兜底才允许动 |
| 7 | **不确定信息标注「待确认」，绝不编造** 字段名/表名/接口名/数据 | AI 幻觉的最大危害是"编得很像真的" |

## 输出与汇报规范

1. 结论先行：第一句给结论/判断，再展开依据
2. 表格 + 阿拉伯数字编号组织内容
3. 收尾三件套：改动文件清单（精确到行号）+ 自检结论 + 下一步建议
4. 只改问题文件，不顺手重构无关代码

## 维护与演进红线（4 条，实战教训固化）

1. **不做项目专属角色**：角色资产全局共享、项目差异放项目 rules——专属版必然跨项目漂移（实测确认）
2. **新角色先以全局通用版验证**，确认通用后再考虑是否纳入固定编制
3. **平台机制变化后，先复测再沿用旧资产**（识别方式 / 作用域 / 字段映射）
4. **修改角色文件后，需重新登记并重启验证**——文件就位 ≠ 生效

## 落地方式

- 红线写进每个项目的 `user_rules.md`（见 `templates/user-rules-template.md`）→ AI 每次开工自动读
- 独立审查角色（@code-reviewer）的报告**必须含红线核验节**，只读目录零改动要列证据
- 提交前跑 `scripts/check_roles.py`，泄漏扫描自动拦截公司信息进入公开仓库
