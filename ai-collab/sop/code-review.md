# 代码审查 SOP（七步）

> 背景：AI 写的代码必须经过**独立审查**再交付——写代码的人不审查自己的代码（自我辩护倾向）。
> 执行者：@code-reviewer（独立审查官，只读审查、绝不改代码）。
> 完整可加载版本见 `roles/code-reviewer.md`，本文件为方法论速览。

## 七步流程

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1. 确认范围 | 读用户指定的包/目录，列出全部待审文件清单（含路径） | 待审清单 |
| 2. 六维审查 | 功能正确性 / 架构符合性 / 安全 / 异常与事务 / 规范 / 风格对齐 | 逐维问题 |
| 3. 并发与幂等专项 | 金额/状态变更/到账类路径：条件更新抢占、重复请求幂等 | 专项结论 |
| 4. 红线核验 | 只读目录零改动（列证据）、无违反项目红线代码 | 红线核验节 |
| 5. 问题清单表 | `P0/P1/P2/P3 | 文件:行号 | 问题 | 修复建议` | 结构化清单 |
| 6. 结论 | P0/P1 数量、是否可交付、本地演示/联调影响、对接真实环境前必修项 | 总评 |
| 7. 落盘 | 报告写入 devlog：`代码审查_<范围>_<日期>.md`（含日期防覆盖） | 审查报告文件 |

## 六维审查框架

| 维度 | 查什么 |
|---|---|
| 功能正确性 | 对照需求文档：状态流转是否覆盖、金额单位统一、边界情况（空/超时/重复请求/迟到回调） |
| 架构符合性 | 分层是否干净（controller→service→mapper→entity）；有无直连/越层（如只读系统被读写） |
| 安全 | 持久层写法（禁 `${}` 拼接）、参数校验完整性、防越权、密钥/凭证不硬编码、日志不泄露敏感信息 |
| 异常与事务 | 事务边界是否准确、异常是否被吞、统一返回结构是否一致、回调/通知语义是否会被对端误判 |
| 规范 | 命名、软删除约定、时间字段、无硬编码业务值（以项目 rules 为准） |
| 风格对齐 | 与同模块已交付写法保持一致，不发明新风格 |

## 问题分级定义

| 级别 | 含义 | 处置 |
|---|---|---|
| P0 | 阻断：金额错误/数据损坏/安全漏洞/只读系统被改动 | 必修，禁止交付 |
| P1 | 应修：明显 bug / 违反项目红线 | 交付前必须修完 |
| P2 | 建议：可优化项 / 潜在风险 | 择机修 |
| P3 | 可选：风格/微调 | 参考 |

## 审查者铁律
1. 只读审查：Read/Glob/Grep 读代码；唯一写操作是落盘审查报告
2. **绝不 Edit 任何代码文件**——发现问题只出清单，修复由用户确认后另行安排
3. 每条问题必须给「文件路径:行号」，不确定的标注「待确认」，绝不编造
4. 报告结论先行：第一行总评（P0/P1 数量 + 是否可交付），再给问题表
