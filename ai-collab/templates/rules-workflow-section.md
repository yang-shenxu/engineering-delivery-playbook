# 工作风格节 · 通用模板（追加到项目 rules 文件末尾）

> 用法：把下方整段追加到任意项目的 `.trae/rules/user_rules.md`（或约定规则文件）末尾。
> 这是所有项目统一的标准段，替换完项目骨架的其余占位符后**保留本节原样**。
> `install.sh` 会自动完成追加；手动操作时直接复制粘贴。

```markdown
## 工作风格与协作规范

### 汇报格式（每次回复默认遵守）
1. 结论先行：第一句给结论/判断，再展开依据
2. 表格 + 阿拉伯数字编号组织内容（禁罗马数字/汉字编号）
3. 数值保留两位小数；禁止"开发中"等未完成字眼（已完成/待办/阻塞说清）
4. 收尾三件套：每次任务结束必须输出「改动文件清单 + 自检结论 + 下一步建议」

### 默认开发节奏（除非用户另有指示）
1. 开工先读：本规则文件 + 最新进度/日志文件，对齐上下文再动手
2. 方案先行：新功能/新表/新接口，先出方案落盘到 docs 约定目录，等用户确认再编码
3. 编码对齐：与项目已交付模块的分层与写法保持一致，不发明新风格
4. 交付自检：编译级零错误 + 红线自查 + 收尾三件套
5. 汇报附改动文件清单与行号，不夸大、不省略

### 红线（最高优先级）
1. 不打包、不部署、不启动服务、不测试接口、不执行 SQL（DDL 只出脚本）
2. 严禁乱改配置文件（application.yml 等），如需修改先征求同意
3. 涉及生产/现场/线上的改动，改前先 git 备份/确认版本
4. 不确定信息标注「待确认」，绝不编造字段名/表名/接口名/数据

### Subagent 协作（用户会 @ 调用，subagent 文件见 .trae/agents/）
| Subagent | 用途 | 调用时机 |
|---|---|---|
| @architect | 架构分析/方案设计/结构评审 | 新任务开工、跨模块改造前 |
| @code-reviewer | 独立深度审查（P0/P1/P2 问题清单） | 模块/功能点交付后 |
| @doc-keeper | 文档结构合规检查、归档建议、维护 00-文档索引 | 新文档落盘前、docs/ 混乱时 |
| @requirement-clarifier | 需求澄清（先问清再动工） | 新需求/含糊任务动工前 |
- 收到 P0/P1 修复清单时：只出修复方案，用户确认后才动手；只改问题文件，不顺手重构
```
