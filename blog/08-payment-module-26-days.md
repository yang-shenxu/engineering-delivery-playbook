# 一个支付模块的 26 天：我把倒排时间线摊开给你看

> 系列第 8 篇。前几篇讲了交付 SOP 的骨架（九步走 / 三道闸门 / 十条纪律）和两个大坑（本地全绿 / 交付了≠生效了）。这篇换个角度：把一个真实支付模块从立项到全量上线的 **26 天时间线**完整摊开——不谈方法论，只看**时间到底花在了哪儿**。答案可能和你想的不一样：纯写代码只占 5 天。

## 一、先看全貌

一个停车费抵扣支付模块（外挂式：对方系统一行代码不能改），从立项到全量上线：

| 相对时间 | 阶段 | 关键事件 |
|---|---|---|
| **D-26** | 立项与口径锁定 | 角色定位、关键口径书面确认、生产链路打通 |
| **D-18** | 建模与数据同步 | 表设计（14 张）+ 增量同步脚本 + 基础数据首次同步 |
| **D-17** | 契约与设计 | 接口契约 + 业务层设计（事务边界 / 回滚矩阵 / 状态判定优先级） |
| **D-14 ~ D-10** | **开发（5 天）** | 主链路 / 附加逻辑 / 适配层 / 冲正——**全程 4 轮独立复核** |
| **D-8** | 静态闭环 | 涉资缺陷全部闭环 |
| **D-7** | **入口上线** | 双节点部署 + 独立入口 + DNS，公网可达（早于截止日 2 天） |
| **D-6** | 涉资缺陷修复 | 预算封顶语义错位修复 + 运行期验证 |
| **D-5** | 部署与运维底座 | 新版本双节点 + 服务托管化 + 备份四层 + 台账独立 |
| **D-4** | 数据缺口发现 | 基础数据 20% 缺口 → 当日重导补齐 |
| **D0** | **首次完整发布** | 新版本双节点 + 入口补齐 + 修掉"只改一台"的历史隐患 |
| **D+2** | 全量上线 | 平台方全量切量 |

先说三个反直觉的观察：

1. **纯编码只占 5 天（19%）**——D-14 到 D-10。剩下 21 天在做口径、契约、复核、验证、部署、数据。
2. **"入口上线"（D-7）比"功能写完"（D-10）更早**——先让通道可达，再往里填功能。上线不是一个事件，是一个持续状态。
3. **D-4 还在补基础数据**——代码全写完了，一块 20% 缺口的基础数据差点让整个活动空转。

## 二、时间花在哪了：逐段拆

### D-26 ~ D-18（8 天）：把"能确定的"钉死

这 8 天一行业务代码都没写。做的事：

- **角色表 + 称谓铁律**：三方对接（业主 / 停车平台方 / 甲方技术方），谁负责"绑车牌找账户"、谁负责"扣款切地址"，逐条写死——**称谓一旦定错 = 责任归属错**，后期所有扯皮都源于这里没钉死
- **口径确认单**：活动期、预算上限、抵扣比例、取整规则——全部书面确认。分歧项不开放式提问，给"我方默认口径"让对方二选一
- **表设计 + 增量同步**：14 张表的库不是拍脑袋建的，是按事务边界总表反推的

> 为什么值 8 天：这个模块的资金流向是"券 → 虚拟账户 → 银行快捷支付"三段，任何一段的口径模糊都会变成上线的资金事故。**前期钉死的每一条口径，都是后期少返的一天工。**

### D-17（1 天）：契约与设计，编码的"施工图"

接口契约、字段对照表、事务边界总表、回滚矩阵——**一天出齐**，然后编码方照着写、无需再问。

其中最值钱的一张表是事务边界：

| 步骤 | 事务 | 失败处理 |
|---|---|---|
| 本地资源核销（券） | 外层事务 | 抛异常整体回滚 |
| **外部扣款调用** | 🔴 **独立事务** | 先落流水后调通道；未知状态留"待确认"交补偿 |
| **附加动作（返券）** | 🔴 **独立事务（提交后）** | 附加失败绝不复主交易 |

> 为什么值 1 天：外部扣款放进外层事务 = "对方已扣款、本地已回滚"的资金事故。这张表把最容易翻车的地方在编码前写死，编码零歧义。

### D-14 ~ D-10（5 天）：开发 + 4 轮独立复核

5 天写完全部代码，**复核用了 4 轮**，挖出 4 条上线级缺陷——全部是"本地全绿、生产失效"型：签名只签 6/30 字段、空值不参与签名、返回字段名想当然、单号前置即占用。

> 为什么复核要 4 轮：每轮都是"独立读码，不采信自述"，同一类 bug 往往有多个取值点——第二轮挖出同源第三处是常态。**复核的产出不是"通过"，是"挖出"。**

### D-7：入口上线比功能完工更早

功能 10 号才写完，7 号就把入口部署上生产了（独立 vhost + DNS，公网可达）——**早于截止日 2 天**。

这不是冒进，是策略：**通道先通，功能后填**。DNS 解析、证书、网关路由、负载均衡这些"基础设施问题"和业务代码无关，越早暴露越好。等代码写完才第一次部署，遇见 DNS 问题就是 Pure delay。

### D-6 ~ D-4：三个"以为完了"的陷阱

- **D-6 涉资缺陷**：预算封顶的语义理解错位——"封顶"是"超过就拒绝"还是"超过截断"？一字之差，资金事故。修复 + 运行期验证
- **D-5 运维底座**：服务托管化（systemd）+ 备份四层（脚本/定时/恢复演练/跨机副本）——上线不是"跑起来"，是"能被运维"
- **D-4 数据缺口**：基础数据同步完一查覆盖率——**20% 缺口**。数据"陈旧"没有告警，不主动核对永远不会被发现。当日重导补齐

> 这三天的共同点：**都在"功能写完"之后**。代码写完只是完成了一半——语义对齐、运维就绪、数据就绪，才是能上线的完整定义。

### D0 ~ D+2：发布与全量

首次完整发布（两台错开重启、逐台验证），D+2 平台方全量切量。发版纪律：每包记 jar 名 + sha256 + 回滚目标包——之后上线后 17 天里 5 次换包，零回滚事故。

## 三、可抄的时间线模板

把这次 26 天的时间分配抽象出来，就是一个支付类外挂模块的排期模板：

| 阶段 | 占比 | 内容 |
|---|---|---|
| 口径与勘察 | ~30% | 角色铁律 / 口径确认单 / 现状勘察 / 冲突预判 |
| 契约与设计 | ~5% | 字段对照 / 事务边界 / 回滚矩阵（一天出齐） |
| 开发+复核 | ~20% | 纯编码 5 天，复核与编码交替进行 |
| 部署与验证 | ~25% | 入口先上 / 逐台部署 / mock 验证 / 真车联调 |
| 缺口与收尾 | ~20% | 数据覆盖率核对 / 运维底座 / 首发与全量 |

**核心规则只有一条：先通再全，先证再信。** 入口上线早于功能完工；每一步的"完成"都有取证判据。

## 四、写在最后

26 天里最忙的不是写代码的 5 天，而是 D-7 前后的部署验证期和 D-4 的数据抢救。回头看，如果口径没提前钉死、契约没提前成文，开发就不止 5 天——**前期"慢"的 8 天，换来了编码期零需求变更、零口径扯皮。**
