# CASE STUDY 01 · 火电报表系统 N+1 查询优化

## 让四张"老慢报表"从数千次 SQL 降到 1 次

**一句话摘要**：在不改业务逻辑、不新增 SQL、不碰数据库结构的前提下，用"批量 IN 查询 + 内存 Map 索引"重构火电节能分析四张存量报表的取数逻辑，SQL 调用从每张约 3000 次 / 1000 次降至 1~2 次，接口从"打开就卡"变为秒开。这是同一套性能优化方法论在存量代码上的收官应用。

---

## 1. 背景：四张"老报表"为什么慢

火电节能分析有四张报表（节能值际分析、全厂节能值际分析、节能日分析、全厂节能日分析），是运维人员日常查看能耗的核心报表。历史代码采用**循环逐条查库（N+1）**模式：

- 值际类两张：外层按班组（约 30 天 × 3 班 ≈ 90 个）× 内层真实测点（约 33 个）双重循环，每组合调一次 SQL → **每张约 3000 次 SQL**
- 日分析类两张：外层按天（约 30 天）× 内层测点（约 33 个）→ **每张约 1000 次 SQL**

单条 SQL 本身不慢，但累计上千次数据库往返，接口响应被拖到分钟级——用户点开报表就转圈。

## 2. 根因诊断

四张表结构完全同构，瓶颈一模一样：**循环里逐条查库**。幸运的是 Mapper 层已有现成的批量方法（此前开发新报表时沉淀），本次无需新增 SQL、无需 DDL，纯代码层改造。

## 3. 解决方案（四步模板，业务零改动）

1. **收集真实测点 saveId**：遍历报表配置，跳过"计算列"和无测点项，只收集真实测点
2. **一次批量查询**：把收集到的 saveIds 一次性 IN 查完，每张表 1~2 次 SQL 拉全量数据
3. **内存 Map 索引**：构建 `Map<时间区间, Map<saveId, 值>>`，原循环内 O(1) 取值，替代逐条查库
4. **业务逻辑保持原样**：动态表头读取、计算列公式、总计行、返回结构全部不变

## 4. 量化结果

| 报表 | 改前 SQL 次数 | 改后 SQL 次数 |
|---|---|---|
| 节能值际分析 | ~3000（班组×测点） | **1** |
| 全厂节能值际分析 | ~3000（班组×测点） | **1** |
| 节能日分析 | ~1000（天×测点） | **2**（日期列表 + 批量） |
| 全厂节能日分析 | ~1000（天×测点） | **2**（日期列表 + 批量） |

## 5. 方法论沉淀（可复用）

- **N+1 优化四步模板**：收集 ID → 一次批量 IN → 内存索引 O(1) 取值 → 业务逻辑不动
- **配置驱动铁律**：表头一律从报表配置表动态读取，禁止硬编码
- **存量代码改造三原则**：不改业务逻辑、不加 DDL、新旧数据逐行对比验收（本次特别验证了批量 SQL 的 `unit_id` 过滤差异，避免漏数）

## 6. 同一方法论的系列战绩（体系化能力）

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 值际月负荷率（新报表） | 450 次 SQL / 40.7s | 2 次 SQL / 亚秒级 |
| 值际指标分析（新报表） | 2700 次 SQL | 4 次 SQL |
| 指标统计分析（新报表） | ~960 网络请求 / 20s | ~96 请求 / 2s |
| **节能四张（老报表存量改造）** | **~3000 次 / 张** | **1~2 次 / 张** |

同一套"批量取数 + 内存索引"方法论，既支撑了 7 张新报表从 0 到 1 的性能设计，也完成了 4 张存量报表的改造——证明不是"只会写新代码"，而是能理解并改进别人的存量系统。
