# Case Study 03 · 火电厂煤质数据自动采集管道（FTP → 时序库）

> 从双 FTP 数据孤岛到无人值守的自动采集管道，2 天从开发到现场交付

**一句话摘要**：在"双 FTP 服务器编码不一致、目录式文件结构、非标准 LIST 格式、复杂 Excel 业务口径、无中间件直写时序库"多重现实约束下，2 天独立交付一条无人值守的数据采集管道——每日 3 班次定时拉取、解析 9 个煤质测点、按统一口径换算、增量写入时序数据库并回读校验，最终以"exe + 离线安装包 + 零编码手册"形态交付现场部署，实施人员无需编写任何代码即可上线运行。

## 1. 背景：两台 FTP 服务器上的数据孤岛

某火电厂煤质化验数据与化学运行班报分散保存在两台独立的 FTP 服务器上：

- FTP1：煤质化验数据（.xls，UTF-8 编码），含入炉煤、炉渣碳等化验结果；
- FTP2：化学运行班报（.xlsx，GBK 编码），按"年月班报"目录组织，含飞灰含碳量等班次数据。

原流程靠人工定期导出、手工整理，无法支撑大屏实时监控与能耗分析对数据的时效性要求。目标：建设一条无人值守的自动采集管道，每日定时从两台服务器拉取文件、解析出关键测点、按统一口径换算后直接写入时序数据库，供大屏与能耗分析使用。

## 2. 现实约束（决定方案形态的五个硬约束）

1. 双源编码不一致：FTP1 为 UTF-8、FTP2 为 GBK，统一编码必然有一侧解码报错；
2. 目录式文件结构：班报按"2026年6月班报"式目录组织，文件随时间滚动，不能写死路径；
3. 非标准 LIST 格式：现场 FTP Server 的 LIST 输出不是标准 Unix 格式，空格切分解析会翻车；
4. 复杂业务口径：样品日期 = 分析日期 − 2 天、同测点新旧系统取均值、空值/0 值不传、部分 sheet 取最新一条；
5. 现场无开发人员：交付对象是实施人员，部署必须零编码。

## 3. 解决方案：五段式管道设计

### ① 采集层：双编码兼容 + 目录模式下载

- 下载函数增加 encoding 参数，FTP1 走 UTF-8、FTP2 走 GBK，且必须在 connect/login 之前设置（服务器初始握手即用编码解析，晚了无效）；
- 新增目录模式下载：CWD 进入目录 → LIST → 正则提取 .xlsx → 按文件名日期排序取最新，并自动检测"当月班报目录"滚动，免人工维护；
- 适配非标准 LIST：正则匹配"HH:MM 之后"的文件名，而不是按空格切分（空格切分会把多余字段拼进文件名导致 550）。

### ② 解析层：双格式 Excel + 9 测点 + 业务口径固化

- 支持 .xls / .xlsx 双格式，提取 9 个关键测点：入炉煤 6 项（收到基全水、灰分、干燥无灰基挥发份、固定碳、全硫、低位发热量）+ 炉渣碳 1 项（煤样加样 sheet 取最新一条）+ 飞灰碳 2 项（甲/乙侧，对应三班制班报）；
- 口径固化：样品日期 = 分析日期 − 2 天，校验不一致时以样品日期列为准；同测点老/新系统值取平均，仅取最新日期组写入；空值/0 值不传，整班次无数据跳过该行，避免污染时序库。

### ③ 写入层：JSONL 直写 + 写后回读校验

- 依据时序库 REST 接口文档，去掉原方案中"CSV 中转 + Jar 包"两个冗余中间环节，直接 POST JSONL 到导入接口，链路更短更稳；
- 写入后自动调用查询接口回读比对数值——写入返回成功不代表数据对，必须回查验证，避免"看起来成功实际错"。

### ④ 调度层：crontab 三班次 + 增量 + 日志轮转

- crontab 配置每日 00:00 / 08:00 / 16:00 自动执行，对齐现场三班制运行节奏；
- 状态文件记录上次最大日期，实现增量导入，只传新数据；
- 日志超 2MB 自动裁剪为最后 300 行，长期运行无运维压力。

### ⑤ 交付层：零编码现场部署

- PyInstaller 打包为 exe；交付文件夹含脚本 + 安装脚本（离线依赖包）+ Linux 部署手册 + 取数逻辑说明；
- 支持环境变量指定日志/状态目录，兼容 exe 与源码两种运行模式；
- 提供本地解析测试、只预览不写入两种调试模式，实施人员可自验。

## 4. 量化结果

- 交付周期：2 天完成开发、联调与交付（开发第 1 天，联调 + 交付第 2 天）；
- 数据覆盖：9 个关键测点（入炉煤 6 + 炉渣碳 1 + 飞灰碳 2）；
- 调度节奏：每日 00 / 08 / 16 三班次自动执行，无人值守持续运行；
- 链路验证：全链路联调通过——写入成功返回，回读查询校验数值一致；
- 增量效率：状态文件增量导入，只传新数据，不重复写入历史；
- 运维成本：日志自动轮转（2MB / 300 行），现场零人工干预。

## 5. 方法论沉淀（可复用）

1. 多看接口文档，少绕路：原方案的 CSV/Jar 中转是过度设计，直连 REST 反而更可靠，联调一次通过；
2. 写后校验是刚需：写入成功不代表数据对，必须回查比对，这条原则适用于所有数据管道；
3. 交付要有"零编码"意识：离线安装包 + 一键脚本 + 详细手册，让非开发人员也能部署，是对接效率的关键；
4. 永远不要假设协议是标准的：现场非标 LIST、双编码这类现实约束，正则是比"空格切分"更稳的选择；
5. 配置与代码分离是开发红线：硬编码连接参数是已知待优化项，下一步应抽到配置文件/环境变量。

## 6. 角色与协作边界

- 独立负责：需求梳理、管道设计、编码、测试、交付物整理全流程，从设计到现场实施部署端到端负责；
- 协作边界：现场 Linux 部署动作由实施团队按手册执行，交付"脚本 + 离线依赖 + 手册 + 自验工具"组合，实施人员零编码完成上线；
- 验收标准：全链路联调通过（写入成功 + 回读校验一致）+ 现场定时任务持续稳定运行。
