# CASE STUDY 04 · 计算引擎"双写管道"升级

## 让时序库里的计算结果，在关系库也能直接查

**一句话摘要**：在不改动计算引擎时序库主链路的前提下，把计算结果旁路同步写入关系库（同源双容器 + 两层幂等 + 异常隔离），业务侧（报表 / 大屏 / 接口）可以直接用 SQL 查计算结果——批量取最新、历史回溯、关联查询不再受时序库查询模式限制。本案例的核心不是"写了多少代码"，而是**方案取舍：为什么第一版被自己否掉**。

---

## 1. 背景：单向链路的业务瓶颈

计算引擎原有链路是单向的：各计算类从**时序库**读原始测点 → 计算 → 结果写回**时序库**。业务侧要用这些结果时，只能再走时序库接口查询。

三类查询在时序库上并不友好：

1. **按任务批量取最新一批计算结果**（报表侧高频）
2. **历史回溯**（跨月对比）
3. **与其他关系表关联查询**（SQL join 是关系库的主场）

需求出现：把计算结果同步落一份到关系库。约束条件只有一条——**不能碰原有时序库写入链路**（那是跑在生产上的主功能）。

## 2. 方案演进：v1 为什么被否掉

这个需求走过两版实现，最终保留第二版。这个取舍过程是本案最值钱的部分。

| 维度 | v1 独立轮询（已废弃） | v2 计算内嵌双写（现行） |
|---|---|---|
| 载体 | 独立定时任务 + 同步 Service | 直接写进各计算类 |
| 触发方式 | cron 每分钟定时轮询 | 跟随计算任务天然触发 |
| 数据来源 | 只能取实时值接口 | 计算过程中已在内存里的结果值 |
| 数据一致性 | 弱：算完与同步存在时间差 | 强：写入的就是本轮计算原值 |
| 冗余开销 | 额外一轮全量测点遍历 | 几乎为零，复用内存数据 |
| 覆盖范围 | 仅实时值，历史/均值类算不了 | 所有计算类按需接入 |

**v1 被否的核心原因**：它是"绕开计算引擎、单独再拉一遍数据"——拿不到历史均值和聚合结果，多出一轮全量遍历开销，还引入时间差。

**v2 的关键判断**：计算结果在写入时序库那一刻，**内存里就已经有完整数据了**——顺手再往关系库插一份，边际成本几乎为零，数据还是本轮计算的原值。

> 可复用经验：当"旁路写入"需求出现时，先找主链路里**已经存在于内存中的那一份数据**，而不是另起一条采集链路。切入点选对了，代码量和数据一致性都会好很多。

## 3. 最终方案设计（三个关键机制）

### 3.1 同源双容器

单个计算类的一次执行：

```
遍历机组 → 连接时序库 → 查计算任务配置 → 遍历测点配置
    ├─ 从时序库读原始数据
    ├─ 计算，结果同时装进两个容器：
    │      tsDataList   → 时序库（原链路，不动）
    │      rdbDataList  → 关系库（新增）
    └─ 循环结束后分别落库
```

两个容器在同一次遍历里填充，**两边数据来源完全一致**——一致性问题在设计层就消掉了，而不是靠事后对账。

### 3.2 两层幂等

重复执行不能灌重复数据，双保险：

1. **业务层**：按计算周期生成确定性 UUID（`年月_机组_测点` 语义），同周期重复计算 → 同一个 UUID → 覆盖而非新增
2. **数据库层**：PostgreSQL upsert 兜底

```sql
INSERT INTO computing_point_value (...) VALUES (...)
ON CONFLICT (uuid) DO UPDATE SET
    point_value = EXCLUDED.point_value, ...
```

> 经验：幂等要做两层——只靠业务层，一旦上层逻辑被改动就会漏；只靠数据库层，UUID 乱生成会造成大量无效更新。

### 3.3 异常隔离（本次升级最重要的安全边界）

两处写入各自 try-catch 包裹，互不影响：

- 时序库写入失败 → 记录日志，关系库照常写
- **关系库写入失败 → 记录日志，绝不影响原有时序库主链路**
- 时序库连接释放移入 `finally`，避免连接泄漏

原则：**新功能是旁路的，它的任何异常都不能反噬原有功能。** 所有新增外部依赖，第一件事是问"它挂了会怎样"。

### 3.4 分区字段补课

表设计后期补了 `date_part`（如 `202609`）分区字段：早期只按任务 UUID 查，历史数据堆在一起没法区分月份；加分区后按月查询、按月清理都直接走索引。

## 4. 亮点算法：条件筛选型聚合

"上月平均值-带前提"这类需求，不是简单求均值，而是**按另一个测点的条件筛选后再求均值**（如"负荷 > 阈值时某测点的平均值"）。实现分两步：

1. 按固定间隔（如 300 秒）取条件测点的**快照序列**
2. 逐快照时刻回查原始测点值，按符号条件（`>` `<` `=`）筛选后累加

为什么用两步法而不是一次拉全量再筛？整月原始数据量大，一次全量拉取内存压力大。两步法把数据规模压到可接受范围，代价是 N 次单点查询——**用请求次数换内存，在离线计算场景是划算的**。

## 6. 方法论沉淀（可复用）

1. **旁路需求优先复用主链路内存数据**，不另起采集链路——切入点决定成败
2. **新功能必须做异常隔离**：新增依赖挂掉时不能拖垮主链路
3. **幂等做两层**：业务层确定性主键 + 数据库层 upsert，互为兜底
4. **补功能顺手补可观测性**：裸 `println` 换成带 `[任务名][机组名]` 前缀的分级日志，多机组排障刚需
5. **调试态代码必须有收口动作**：临时 cron / 临时注释，功能完成时即复原
6. **DDL 与改动记录随功能同步沉淀**：事后靠两份源码目录 diff 还原改动清单的成本，远超当初记一笔
