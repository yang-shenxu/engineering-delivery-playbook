# CASE STUDY 05 · 停车消费券外挂式交付：从 0 到上线运营（48 人日）

## 一类"硬约束项目"的完整走法：外挂式 + 三方对接 + 硬截止 + 生产库只读 + 甲方资产

**一句话摘要**：为某市级生活服务平台交付"停车消费券"模块——停车平台方只改一个扣款域名指向我方服务，由我方按 **券 → 平台虚拟账户 → 银行快捷支付** 三段抵扣停车费，只回成败、成功即抬杆。从立项到首次发布 **26 天**，上线后完成国庆活动运营与三轮功能迭代。本案例的核心不是代码量，而是：**当五条硬约束同时存在时，流程怎么设计、质量怎么守住、出了问题怎么不甩锅。**

---

## 1. 背景：五条硬约束，决定了一切设计

地方平台要做"本地消费留存量"的运营抓手：以「免费停车 + 返券」引导市民绑车牌、用无感支付自动抬杆。我方承接该模块的委托开发与上线后运维全责。

接手时面对的不是普通开发任务，而是五条同时成立的硬约束：

| # | 特征 | 由此决定的流程要求 |
|---|---|---|
| 1 | **外挂式**——对方系统一行代码不能改 | 一切改动走独立服务 + 独立入口；原系统源码只读 |
| 2 | **三方对接**——业主 / 停车平台方 / 甲方技术方 | 必须建角色铁律与对外台账；提问按渠道拆分 |
| 3 | **硬截止**——国庆活动窗口 | 设闸门与降级触发条件；截止后不引变更 |
| 4 | **生产库只读**——原生产库不给写 | 新数据全部放自建库；跨库取数走导出/导入 |
| 5 | **跑在甲方资产上**——服务器是甲方的 | 部署逐台，避免全量中断；对外表述明确资产归属 |

> 这五条不是场景描述，是**约束推导**：每一条都直接决定一类流程动作。后来这个推导表本身成了模板——再接到同类项目，先填表再开工。

## 2. 架构：独立服务 + 独立入口 + 自建库

```
停车平台（改扣款域名指向我方）
      ↓
[入口 vhost：扣款路径截我方，其余透传回平台]
      ↓
[外挂服务 Spring Boot + MyBatis-Plus + PostgreSQL（自建库 14 表）]
   三段抵扣：券核销 → 虚拟账户 → 银行快捷支付（兜底）
      ↓
[生产库 MySQL 只读：用户数据每日增量同步（幂等 upsert）]
```

三个关键设计：

1. **入口层"截流 + 透传"**：nginx vhost 只把扣款相关路径导向我方，其余请求原样透传回平台——平台侧改动被压缩到"改一个域名"。
2. **自建库 + 只读同步**：原生产库 230 张表只读，用户数据通过每日增量同步进自建 PG（近 7 天窗口 + `ON CONFLICT` 幂等），主库零写入风险。
3. **事务边界成文**：外部扣款调用与返券等附加动作**独立事务**（绝不能在外层事务里）——否则会出现"外部已扣款、本地已回滚"的资金不一致。这张事务边界总表在编码前就写死，编码方照着写、无需再问。

## 3. 质量闸门：4 轮独立复核挖出 4 条"本地全绿"型缺陷

开发走"指令 → 交付 → 独立读码复核 → 修复指令 → 再复核"循环，4 轮复核挖出 4 条上线级缺陷，**全部属于"本地全绿、生产失效"型**：

| # | 缺陷 | 根因 |
|---|---|---|
| 1 | 出站签名只签了 6 个字段（报文 30+ 字段） | 照抄了"恰好相等"的旧方法 |
| 2 | 空值不参与签名 | 跨语言隐式转换差异 |
| 3 | 返回字段名想当然（`status` vs `trade_status`） | 未拿对方源码逐字核对 |
| 4 | 单号唯一性约束未知（"先插单再调第三方"，前置即占用） | 未核对方单号生命周期 |

共同根因：**mock 没开验签时怎么跑都全绿**。对策固化为出站接口前置核对清单（状态机 / 唯一性 / 返回键名 / 签名口径）+ mock 照对方口径实现验签且默认开启 + 签名自动化断言。

> 真车联调同样验证了闸门价值：首轮 12 笔仅 2 成功，按"取证 → 定位 → 修复 → 再验"收敛（段2 失败无兜底 → 转段3 兜底；商户号配置是最后一环），修复后全绿，平台方随后全量切量。

## 4. 上线只是及格线：运营期才是主战场

上线后 17 天里完成了 5 次换包与三轮功能迭代，这个阶段沉淀的经验比开发期更值钱：

**发版纪律（5 次换包零事故）**
- 一批换包解决多件事（合批发版），每包记 **jar 名 + sha256 + 回滚目标包**
- 两台服务器**错开重启**、逐台验证——负载均衡下"逐台"是用户无感的唯一保证

**迭代实战**
- **退款接口 + 异步回调**：回调 `appId` 必须用对方接入方配置（不是自己的）、入参类型按对方约定（数字非字符串）、原单去重护栏防重复退款
- **开票两连修**：整包转发把平台侧 `mchId` 字段带出 ⇒ 平台按 `(mchId, appId)` 成对校验失败 ⇒ 修复 = 转发前出"需替换字段清单"；金额字段 `total_amount / goodsAmt / price` **成套同源改**，只改一个 ⇒ 通道侧"金额累加误差"报错
- **未上线模块的定时任务加配置开关**（生产默认关闭）：否则周期性刷异常栈（本项目曾达 5000 行/天），把真实告警淹掉

**运维底座**
- 备份四层：脚本（零密钥）+ 定时任务 + **恢复演练双轮**（数据/属主双对拍）+ 跨机副本
- 回滚三级：功能开关 → 摘除入口（用户无感回原流程）→ 服务回退，触发即执行不等批准
- 每日巡检自动化，但**只取证不归因**——归因必须交叉核对当日变更记录

## 6. 方法论沉淀（可复用）

1. **约束推导表先于方案**：把"外挂式/三方/硬截止/只读/甲方资产"逐条翻译成流程要求，方案自然长出来
2. **出站接口四查**：状态机、唯一性、返回键名、签名口径——全部对着对方源码核，不凭文档
3. **复核对象是现网，不是自述**："指令写了 ≠ 代码里有了"，交付方说"已执行"也要独立取证
4. **事务边界在编码前成文**：外部调用与附加动作独立事务，写进设计文档让编码无歧义
5. **换包三件套**：jar 名 + sha256 + 回滚目标包；两台错开重启
6. **量少 ≠ 我方问题**：上游未就绪时请求根本发不出，使用量不进验收判据
7. **每次返工都变成 SOP**：本项目沉淀 9 步流程 + 3 道闸门 + 10 条纪律 + 22 条上线后增补条目——**能上线靠闸门与回退，能运营靠取证与留痕，能延续靠把每次返工变成 SOP**
